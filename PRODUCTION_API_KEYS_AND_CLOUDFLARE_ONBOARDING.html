Cloudflare Onboarding

Production recommendation: Cloudflare should front the public web and API domains before launch. It gives DNS control, TLS policy, WAF rules, rate limiting at the edge, cache rules for static assets, bot controls, and optional Turnstile challenges for abuse-prone forms.

Domain and DNS setup

  1. Create or use a Cloudflare account.
  2. Add the production domain from Cloudflare Add Site.
  3. Review imported DNS records and add missing records from DNS record setup.
  4. Update nameservers at the registrar to the nameservers Cloudflare provides.
  5. Use proxied records for public web/API hostnames unless a specific service requires DNS-only mode.

TLS, WAF, and cache

  1. Set SSL/TLS mode to Full (strict) once origin certificates are valid.
  2. Enable Managed WAF rules.
  3. Create custom WAF rules for admin, auth, upload, and moderation-sensitive endpoints using custom rules.
  4. Create edge rate limiting for login, registration, password reset, upload, comments, and report endpoints with rate limiting rules.
  5. Use Cache Rules for static assets; do not cache authenticated API responses or user-specific HTML.

Cloudflare API token

The app does not require a Cloudflare runtime token by default. Create a Cloudflare API token only if CI/deploy scripts need to automate DNS, purge cache, manage WAF rules, or call Cloudflare APIs.

  1. Open Create API Token.
  2. Use the narrowest template or custom token possible.
  3. Scope it to the single production zone.
  4. Grant only required permissions, such as Zone DNS Edit, Zone Cache Purge, or WAF Read/Edit when automation needs it.
  5. Store as CLOUDFLARE_API_TOKEN only in deployment secrets, not in source files.

Turnstile option

Add Cloudflare Turnstile if registration, login, password reset, comments, contact, or upload forms receive abuse. Start at Turnstile Get Started and use the widget guidance from Turnstile widget concepts.

Suggested variables: TURNSTILE_SITE_KEY for frontend rendering and TURNSTILE_SECRET_KEY for server-side verification. Add these only when the app code validates Turnstile tokens.

Provider Setup Playbook

PostgreSQL

Primary transactional database for users, uploads, moderation, reports, audit trails, jobs, and app state.

Variables: DATABASE_URL, DATABASE_DIRECT_URL, SHADOW_DATABASE_URL.

  1. Create a production PostgreSQL instance with backups, monitoring, and network restrictions.
  2. Create a least-privilege app user and a separate migration/direct user if your hosting model supports it.
  3. Set pooled and direct URLs in the production secret store.
  4. Run migrations from the deployment workflow, then run the environment doctor.

Application Secrets

Cryptographic secrets for sessions, JWTs, OAuth CSRF state, encrypted OAuth tokens, and signed upload URLs.

Variables: JWT_SECRET, COOKIE_SECRET, OAUTH_STATE_SECRET, OAUTH_TOKEN_ENCRYPTION_SECRET, STORAGE_LOCAL_UPLOAD_SIGNING_SECRET.

Generate a unique value for each variable:

openssl rand -base64 48

Do not reuse values across UAT and production. Do not reuse one generated value for multiple variables.

Sentry

Backend and frontend exception capture, stack traces, release tracking, and incident triage.

Variables: SENTRY_DSN, PUBLIC_SENTRY_DSN, optional SENTRY_AUTH_TOKEN for source maps.

  1. Create backend and frontend projects using Sentry backend setup and Sentry frontend project setup.
  2. Copy each project DSN from the project settings. Sentry explains DSNs in DSN Explainer.
  3. Create an auth token only if the build uploads source maps. Use Sentry auth tokens and the Astro source maps guide.
  4. Set release, environment, and sampling values in production configuration.

Axiom

Structured production logs used for request tracing, abuse investigation, IP/user correlation, and audit evidence.

Variables: AXIOM_TOKEN, AXIOM_DATASET.

  1. Create a production dataset using Axiom Create Dataset or the Axiom UI.
  2. Create a token from Axiom Tokens with ingest access to that dataset.
  3. Confirm ingest behavior with Axiom Ingest.
  4. Use a production-only dataset name such as tfp-production.

Redis

Shared rate-limit and abuse-control state across API instances.

Variable: RATE_LIMIT_REDIS_URL.

  1. Create a managed Redis database. Common options include Upstash Redis or Redis Cloud database setup.
  2. Copy the TLS Redis connection URL into the production secret store.
  3. Restrict network access where supported and set usage alerts.

Resend

Transactional email for verification, password reset, notifications, and account flows.

Variables: RESEND_API_KEY, EMAIL_FROM, SUPPORT_EMAIL, ADMIN_ALERT_EMAIL.

  1. Add and verify the sending domain from Resend Domains.
  2. Create an API key using Resend API Keys or Create an API Key.
  3. Add the DNS records Resend requires through Cloudflare DNS.
  4. Use a restricted production key if your Resend plan supports scoped keys.

Backblaze B2

Object storage for uploads, private moderation artifacts, generated media, and evidence files.

Variables: B2_ACCESS_KEY_ID, B2_SECRET_ACCESS_KEY, B2_BUCKET_NAME, B2_PRIVATE_BUCKET_NAME, BACKBLAZE_*, STORAGE_S3_*.

  1. Create production public and private buckets.
  2. Create limited application keys from Backblaze Application Keys.
  3. If the app uses S3-compatible clients, follow S3-compatible application keys.
  4. Use separate keys for app runtime, workers, and operational tooling when practical.

ImageKit

Image CDN, transformations, upload signing, and optimized media delivery.

Variables: IMAGEKIT_PUBLIC_KEY, IMAGEKIT_PRIVATE_KEY, IMAGEKIT_URL_ENDPOINT, optional IMAGEKIT_UPLOAD_FOLDER.

  1. Create an ImageKit account and media source.
  2. Copy public/private keys from ImageKit API Keys.
  3. Review request signing and API behavior in ImageKit API Overview.
  4. Keep the private key server-only.

Geoapify

Geocoding, map tiles, place search, and location enrichment.

Variable: GEOAPIFY_API_KEY.

  1. Create a project through Geoapify Get Started.
  2. Copy the API key and restrict it where provider controls allow.
  3. Review Maps API and Place Details API if those features are enabled.

Google OAuth

Social login with Google when enabled.

Variables: GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET.

  1. Create or select a Google Cloud project.
  2. Configure OAuth consent and authorized domains.
  3. Create a Web OAuth client using Google API client ID setup.
  4. Manage client credentials from Google OAuth client management.

Apple Sign In

Social login with Apple when enabled.

Variables: APPLE_CLIENT_ID, APPLE_TEAM_ID, APPLE_KEY_ID, APPLE_PRIVATE_KEY.

  1. Enable Sign in with Apple in the Apple Developer account.
  2. Create the private key using Apple private key setup.
  3. Configure service ID, redirect URLs, and domain association.
  4. Keep the private key server-only and rotate through Apple Developer tooling.

Meta Login

Facebook/Meta social login when enabled.

Variables: META_CLIENT_ID, META_CLIENT_SECRET.

  1. Create a Meta app from Create an App.
  2. Add Facebook Login and configure OAuth redirect URLs.
  3. Follow Facebook Login Security for redirect URI validation and app secret handling.

Gemini and Groq

Optional AI generation, translation, moderation assistance, or internal automation features.

Variables: GEMINI_API_KEY, TRANSLATION_GEMINI_API_KEY, GROQ_API_KEY.

  1. Create Gemini keys from Gemini API key docs.
  2. Restrict Google API keys using Google API key restrictions.
  3. Create Groq keys from Groq API Keys and review Groq Quickstart.
  4. Use separate keys per environment and per feature owner where possible.

Google Vision or AWS Rekognition

Direct image moderation provider path if the app does not use the remote moderation service.

Variables: GOOGLE_APPLICATION_CREDENTIALS, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_REGION.

  1. For Google Vision, follow Vision setup and Vision authentication.
  2. For AWS Rekognition, create an IAM user or role with the minimum Rekognition permissions needed by the worker.
  3. Prefer workload identity or instance roles over long-lived static keys when hosting supports it.

Location

Geoapify-backed location autocomplete and reverse geocoding, with Nominatim fallback in code.

Variable: GEOAPIFY_API_KEY.

  1. Create a project through Geoapify Get Started.
  2. Set rate limits and alerts in the provider dashboard.
  3. Use the app database for nearest-user/content ranking; use Geoapify only to resolve user-entered locations to coordinates.

Storage and rotation rules

  • Store real production values only in the deployment secret store or host-level protected environment files.
  • Use separate UAT and production credentials for every provider.
  • Give each token the smallest useful scope and one owner.
  • Rotate immediately after contractor access, suspected exposure, or provider console compromise.
  • Enable billing alerts and quota alerts on every paid provider.
  • Document who owns each provider account and the recovery email or admin group.
Tracing wrong activity: keep Axiom and Sentry enabled, keep API access logs structured, and preserve request metadata such as user ID, session ID, route, action, IP source, Cloudflare country/region/city headers, user agent, upload/comment identifiers, and moderation/report IDs. Never log raw passwords, full OAuth tokens, private keys, payment details, or full bearer tokens.
